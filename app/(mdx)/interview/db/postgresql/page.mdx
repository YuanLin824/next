## 一、基础概念

### Q1: PostgreSQL 和 MySQL 的核心区别？

| 维度         | PostgreSQL                                | MySQL                |
| ------------ | ----------------------------------------- | -------------------- |
| **类型系统** | 极丰富——数组/JSONB/hstore/范围/自定义     | 基础                 |
| **索引**     | 六种（B-Tree/Hash/GiST/GIN/SP-GiST/BRIN） | B-Tree/Hash/Fulltext |
| **MVCC**     | 多版本堆存储（需 VACUUM）                 | undo log 回滚        |
| **复制**     | 物理流复制 + 逻辑复制（原生）             | 异步/半同步          |
| **扩展**     | 极强（PostGIS/pgvector/TimescaleDB）      | 较少                 |
| **连接模型** | 进程（每连接 fork）                       | 线程                 |
| **标准兼容** | 最严格                                    | 较松散               |

### Q2: PostgreSQL 的 Schema 是什么？和 MySQL 的 Database 有什么区别？

```
MySQL:      Database → Table
PostgreSQL: Database → Schema → Table
                       ├── public
                       ├── app
                       └── audit
```

**Schema 的作用：**

- 一个 Database 内组织多组表的命名空间
- 可用于多租户隔离（每个租户一个 Schema）
- `search_path` 控制表查找顺序（类似 $PATH）

```sql
CREATE SCHEMA app;
CREATE TABLE app.users (id SERIAL PRIMARY KEY, name TEXT);
SET search_path TO app, public;
SELECT * FROM users; -- 优先查 app.users
```

### Q3: PostgreSQL 有哪些特色数据类型？

| 类型       | 说明                        | 示例                             |
| ---------- | --------------------------- | -------------------------------- |
| **数组**   | 原生数组类型                | `TEXT[]`, `INT[]`                |
| **JSONB**  | 二进制 JSON，支持索引       | `data @> '{"key": "val"}'`       |
| **hstore** | 键值对                      | `'a=>1,b=>2'::hstore`            |
| **范围**   | int4range/tsrange/daterange | `WHERE ts @> TIMESTAMP '...'`    |
| **枚举**   | 自定义枚举                  | `CREATE TYPE mood AS ENUM (...)` |
| **几何**   | point/line/polygon          | PostGIS 增强                     |
| **UUID**   | 原生 UUID                   | `uuid_generate_v4()`             |
| **INET**   | IP 地址                     | `'192.168.1.1'::inet`            |

### Q4: SERIAL vs IDENTITY 的区别？

```sql
-- SERIAL（老式，非标准 SQL）
CREATE TABLE t1 (id SERIAL PRIMARY KEY);

-- IDENTITY（标准 SQL，推荐 PG 10+）
CREATE TABLE t2 (id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY);
CREATE TABLE t3 (id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY); -- 可手动插入

-- 为什么推荐 IDENTITY？
-- 1. 标准 SQL，可移植
-- 2. 权限分离（不能直接 UPDATE 序列值）
-- 3. ALWAYS 模式防止意外插入 id
```

## 二、MVCC 与事务

### Q5: PostgreSQL 的 MVCC 和 MySQL 的 MVCC 有何不同？

```
PostgreSQL:                     │      MySQL InnoDB:
UPDATE 一行                     │      UPDATE 一行
→ 插入新版本 tuple（新行）      │      → 旧行写入 undo log
→ 旧版本保留在堆表中            │      → 原地更新行
→ VACUUM 定期清理死元组         │      → undo log 自动回收

PostgreSQL 方式：
✅ 不需要 undo log（回滚就是标记死元组）
❌ 需要 VACUUM 回收空间（表膨胀风险）
❌ 索引也需要更新（新 tuple 新 ctid）
```

每行数据有两个系统列：

- `xmin`：创建该行的事务 ID
- `xmax`：删除该行的事务 ID（0 = 未删除）

**快照判断可见性：** 事务通过快照（Snapshot）判断 xmin/xmax 对应的行是否对当前事务可见。

### Q6: PostgreSQL 的隔离级别和 MySQL 有什么不同？

| 隔离级别                   | PG 实现                 | 说明                            |
| -------------------------- | ----------------------- | ------------------------------- |
| READ UNCOMMITTED           | 等同于 READ COMMITTED   | PG 不允许脏读                   |
| **READ COMMITTED**（默认） | 每次语句看最新快照      | —                               |
| REPEATABLE READ            | 事务内同一切片          | PG 中无幻读（快照隔离天然解决） |
| **SERIALIZABLE**           | SSI（可串行化快照隔离） | 真正可串行化，不靠锁            |

**关键差异：** PG 的 REPEATABLE READ 通过快照隔离天然防幻读；SERIALIZABLE 基于 SSI 算法而非锁表。

### Q7: VACUUM 的作用是什么？autovacuum 如何工作？

```sql
-- VACUUM：标记死元组空间为可重用（不锁表，不归还磁盘）
VACUUM users;

-- VACUUM FULL：锁表重写，归还磁盘给 OS（慎用——阻塞读写）
VACUUM FULL users;

-- ANALYZE：更新统计信息（优化器依赖）
ANALYZE users;
```

**autovacuum** 自动在后台执行 VACUUM + ANALYZE。触发条件：

```sql
-- 死元组数 > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * 表行数
-- 默认：死元组 > 50 + 0.2 * 行数 → 触发
```

**事务 ID 回卷（wraparound）保护：** xid 是 32 位的，快到上限时 autovacuum 强制冻结（freeze）旧行，防止回卷导致数据消失。

### Q8: PostgreSQL 有哪些锁级别？

| 锁级别（由低到高） | 获取方式                               |
| ------------------ | -------------------------------------- |
| Access Share       | SELECT                                 |
| Row Share          | SELECT FOR UPDATE/SHARE                |
| Row Exclusive      | INSERT/UPDATE/DELETE                   |
| Share              | CREATE INDEX (without CONCURRENTLY)    |
| Access Exclusive   | ALTER TABLE / DROP TABLE / VACUUM FULL |

> PG 读不阻塞写，写不阻塞读——**SELECT 永远不会被 INSERT/UPDATE/DELETE 阻塞**。

## 三、索引

### Q9: PostgreSQL 的六种索引类型及其适用场景？

| 类型               | 适用                              | 操作符                                    |
| ------------------ | --------------------------------- | ----------------------------------------- |
| **B-Tree**（默认） | 等值、范围、排序                  | `<` `<=` `=` `>=` `>` `BETWEEN` `IS NULL` |
| **Hash**           | 等值查询                          | `=`（10+ 支持 WAL）                       |
| **GiST**           | 全文搜索、几何数据、范围          | `@>` `<@` `&&`                            |
| **GIN**            | JSONB、数组、全文搜索（倒排索引） | `@>` `?` `?&` `?\|`                       |
| **SP-GiST**        | 非平衡结构（点、范围）            | 类似 GiST                                 |
| **BRIN**           | 超大顺序表（时序、日志）          | 范围扫描（块级，极小）                    |

```sql
-- 关键示例
CREATE INDEX idx_tags ON users USING GIN (tags);            -- 数组
CREATE INDEX idx_config ON configs USING GIN (data);        -- JSONB
CREATE INDEX idx_logs_time ON logs USING BRIN (created_at); -- 时序数据
```

### Q10: 部分索引和覆盖索引怎么用？

```sql
-- 部分索引——只索引符合条件的行（更小、更快）
CREATE INDEX idx_active_users ON users (id)
WHERE status = 'active';

-- 覆盖索引（INCLUDE 非键列，避免回表）—— PG 11+
CREATE INDEX idx_users_email ON users (email) INCLUDE (name, age);
-- SELECT email, name, age FROM users WHERE email = 'x' → Index Only Scan ✅

-- 表达式索引
CREATE INDEX idx_lower_email ON users (LOWER(email));
SELECT * FROM users WHERE LOWER(email) = 'alice@x.com'; -- 走索引
```

## 四、高级特性

### Q11: CTE 和递归 CTE 的用法？

```sql
-- 普通 CTE
WITH active_stats AS (
  SELECT status, COUNT(*) AS cnt FROM users GROUP BY status
)
SELECT * FROM active_stats WHERE cnt > 10;

-- 递归 CTE —— 树形/层级数据
WITH RECURSIVE tree AS (
  -- 基础：根节点
  SELECT id, name, parent_id, 0 AS level
  FROM categories WHERE parent_id IS NULL
  UNION ALL
  -- 递归：子节点
  SELECT c.id, c.name, c.parent_id, t.level + 1
  FROM categories c
  JOIN tree t ON c.parent_id = t.id
)
SELECT repeat('  ', level) || name AS tree_view FROM tree;
```

### Q12: JSONB vs JSON 的区别？

|        | JSON                     | JSONB        |
| ------ | ------------------------ | ------------ |
| 存储   | 文本（保留空格和键顺序） | 二进制解析   |
| 索引   | ❌                       | ✅ GIN       |
| 写入   | 快                       | 慢（需解析） |
| 查询   | 慢（每次解析）           | **快**       |
| 重复键 | 保留                     | 只留最后一个 |

```sql
-- JSONB 操作符
SELECT data->>'key' FROM t;                -- 取文本值
SELECT * FROM t WHERE data @> '{"k":"v"}'; -- 包含检查（走 GIN 索引）
```

## 五、运维

### Q14: pg_dump 和 pg_dumpall 的区别？

```bash
pg_dump -U postgres mydb > db.sql       # 单库备份
pg_dump -U postgres mydb -Fc -f db.dump # 自定义格式（可并行恢复）
pg_dump -U postgres mydb --schema-only  # 仅结构

pg_dumpall -U postgres > all.sql        # 全实例备份（含用户/角色）
```

### Q15: 流复制的工作原理？

```
Primary                 Standby
  │                        │
  │ 写入 → WAL             │
  │                        │
  └─── WAL Sender ──▶ WAL Receiver ──▶ 重放 WAL ──▶ 同步
                     (流复制)
```

**同步 vs 异步：** `synchronous_commit = on` → 等 Standby 确认后才返回客户端（强一致，性能下降）。
