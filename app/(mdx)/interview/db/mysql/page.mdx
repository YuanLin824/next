## 一、基础概念

### Q1: MySQL 有哪些存储引擎？InnoDB 和 MyISAM 的区别？

| 特性          | InnoDB           | MyISAM         |
| ------------- | ---------------- | -------------- |
| **事务**      | ✅ ACID          | ❌             |
| **行级锁**    | ✅               | ❌（仅表锁）   |
| **外键**      | ✅               | ❌             |
| **MVCC**      | ✅               | ❌             |
| **崩溃恢复**  | ✅（redo log）   | ❌             |
| **全文索引**  | ✅（5.6+）       | ✅             |
| **count(\*)** | 慢（逐行扫描）   | 快（存了行数） |
| **适用场景**  | **一切生产环境** | 已淘汰         |

> MySQL 8.0 已将系统表全部迁移到 InnoDB，MyISAM 不再推荐使用。

### Q2: CHAR 和 VARCHAR 的区别？什么场景用哪个？

|          | CHAR(N)                               | VARCHAR(N)                               |
| -------- | ------------------------------------- | ---------------------------------------- |
| 存储方式 | 定长，不足补空格                      | 变长，按实际长度 + 1-2 字节前缀          |
| 最大长度 | 255 字符                              | 65535 字节（实际约 16383 字符，utf8mb4） |
| 空间效率 | 浪费（定长）                          | 节省                                     |
| 读写效率 | **更快**（定长偏移计算）              | 略慢（需读前缀）                         |
| 适用     | MD5值、身份证号、状态码等**定长数据** | 绝大多数文本字段                         |

### Q3: TEXT 和 VARCHAR 有什么区别？

|          | VARCHAR            | TEXT                   |
| -------- | ------------------ | ---------------------- |
| 存储位置 | 行内（≤ 页大小/2） | 行外（仅存指针）       |
| 最大长度 | 65535 字节         | 4GB（取决于类型）      |
| 默认值   | 支持               | **不支持**             |
| 索引     | 全字段索引         | 只能前缀索引           |
| 临时表   | 内存临时表         | 磁盘临时表（降低性能） |

### Q4: 为什么金额要用 DECIMAL 而不是 FLOAT/DOUBLE？

```sql
-- FLOAT/DOUBLE 是近似值（IEEE 754），存在精度丢失
SELECT 0.1 + 0.2 = 0.3;            -- → 0（false!）
SELECT 0.1 + 0.2;                   -- → 0.30000000000000004

-- DECIMAL 是定点精确存储
SELECT CAST(0.1 AS DECIMAL(10,2)) + CAST(0.2 AS DECIMAL(10,2)); -- → 0.30（精确）
```

**原理**：DECIMAL 以字符串/二进制形式存储每一位数字，不存在二进制浮点数的精度丢失。金额、金融数据必须用 DECIMAL(M,D)。

### Q5: COUNT(1)、COUNT(\*)、COUNT(col) 的区别？

```sql
-- COUNT(*)：统计所有行数（含 NULL），InnoDB 会选择最小的索引扫描
SELECT COUNT(*) FROM users;

-- COUNT(1)：等价于 COUNT(*)，每一行都返回 1 再计数
SELECT COUNT(1) FROM users;

-- COUNT(col)：只统计 col IS NOT NULL 的行
SELECT COUNT(email) FROM users; -- 有 email 的行数
```

**性能**：`COUNT(*)` = `COUNT(1)` > `COUNT(col)`。`COUNT(*)` 在 MySQL 8.0 已专门优化。

## 二、索引

### Q7: MySQL 索引的底层数据结构是什么？为什么用 B+Tree？

InnoDB 使用 **B+Tree**：

```
                [30 | 60]              ← 非叶子节点：只存键 + 指针
               /    |    \
        [10|20]  [40|50]  [70|80]       ← 高度通常 ≤ 3-4
        /  |  \   ...       ...
       → 叶子节点：双向链表，存完整数据/主键值
```

**B+Tree vs B-Tree vs Hash：**

| 特性     | B+Tree               | B-Tree | Hash       |
| -------- | -------------------- | ------ | ---------- |
| 范围查询 | ✅（叶子节点链表）   | ✅     | ❌         |
| 等值查询 | ✅                   | ✅     | ✅（更快） |
| 排序     | ✅                   | ✅     | ❌         |
| 最左前缀 | ✅                   | ✅     | ❌         |
| 磁盘 IO  | 最少（度大，高度低） | 少     | —          |

**为什么不用二叉树/红黑树？** 二叉树高度 O(log₂N) → 100 万行高度约 20 → 20 次磁盘 IO。B+Tree 每个节点存 1000+ 个键 → 100 万行高度约 2-3 → 2-3 次磁盘 IO。

### Q8: 聚簇索引和二级索引的区别？什么是回表？

```
聚簇索引（Clustered Index）：             二级索引（Secondary Index）：
叶子节点存的是「整行数据」                叶子节点存的是「主键值」

表数据本身就是按主键 B+Tree 组织的        查到主键后 → 再查聚簇索引取完整行
= 数据就是索引，索引就是数据               这个过程叫「回表」

● 一张表只能有一个聚簇索引                  ● 可以有多个二级索引
● 主键默认就是聚簇索引                      ● 唯一索引/普通索引都是二级索引
```

```sql
-- 回表示例
SELECT * FROM users WHERE email = 'alice@x.com';
-- 1. 查 idx_email (二级索引) → 得到 id = 42
-- 2. 用 id=42 查聚簇索引 → 得到完整行 ← 这就是回表
```

**覆盖索引（避免回表）：**

```sql
-- 查询的所有列都在索引中 → 不回表，性能最优
CREATE INDEX idx_cover ON users (email, name, age);
SELECT email, name, age FROM users WHERE email = 'alice@x.com';
-- Extra: "Using index" ✅ 纯索引扫描
```

### Q9: 复合索引的最左前缀原则是什么？

```sql
CREATE INDEX idx_a_b_c ON t (a, b, c);

-- ✅ 能用到索引
WHERE a = 1                          -- 用到 a
WHERE a = 1 AND b = 2                -- 用到 a, b
WHERE a = 1 AND b = 2 AND c = 3      -- 用到全部
WHERE a = 1 AND c = 3                -- 只用到 a（c 被跳过，无法使用）
WHERE a > 1 AND b = 2                -- 用到 a（范围条件后 b 失效）

-- ❌ 不能用到索引
WHERE b = 2                          -- 违背最左前缀
WHERE c = 3                          -- 违背最左前缀
WHERE b = 2 AND c = 3                -- 违背最左前缀
```

**复合索引列顺序的 ESR 规则：** Equality（等值）→ Sort（排序）→ Range（范围）。

### Q10: EXPLAIN 的关键字段怎么解读？

```sql
EXPLAIN SELECT * FROM users WHERE email = 'alice@x.com';
```

| 字段    | 含义                 | 关键值                                                                                                   |
| ------- | -------------------- | -------------------------------------------------------------------------------------------------------- |
| `type`  | 访问类型（从好到坏） | `const`(主键/唯一等值) > `ref`(索引等值) > `range`(索引范围) > `index`(全索引扫描) > **`ALL`**(全表扫描) |
| `key`   | 实际使用的索引       | NULL = 没用索引                                                                                          |
| `rows`  | 预估扫描行数         | 越小越好                                                                                                 |
| `Extra` | 额外信息             | `Using index`(覆盖索引✅) / `Using filesort`(额外排序⚠️) / `Using temporary`(临时表❌)                   |

### Q11: 索引失效的常见场景有哪些？

```sql
-- 1. WHERE 中对列做函数/运算
❌ SELECT * FROM users WHERE YEAR(created_at) = 2026;
✅ SELECT * FROM users WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';

-- 2. 隐式类型转换（列是 VARCHAR，值传了数字）
❌ SELECT * FROM users WHERE phone = 13800000000;
✅ SELECT * FROM users WHERE phone = '13800000000';

-- 3. LIKE 前导模糊
❌ SELECT * FROM users WHERE name LIKE '%alice';
✅ SELECT * FROM users WHERE name LIKE 'alice%';

-- 4. 负向条件
❌ SELECT * FROM users WHERE status != 'banned';
❌ SELECT * FROM users WHERE id NOT IN (1, 2, 3);
-- 负向条件通常不走索引（优化器可能选择全表扫描）

-- 5. OR 条件中有一个没索引 → 全表扫描
❌ SELECT * FROM t WHERE indexed_col = 1 OR unindexed_col = 2;
```

## 三、事务与锁

### Q12: MySQL 的事务隔离级别有哪些？

| 隔离级别            | 脏读 | 不可重复读 | 幻读       | 默认              |
| ------------------- | ---- | ---------- | ---------- | ----------------- |
| READ UNCOMMITTED    | ✅   | ✅         | ✅         | —                 |
| READ COMMITTED      | ❌   | ✅         | ✅         | PostgreSQL/Oracle |
| **REPEATABLE READ** | ❌   | ❌         | ❌（部分） | **MySQL InnoDB**  |
| SERIALIZABLE        | ❌   | ❌         | ❌         | —                 |

```sql
-- 查看当前隔离级别
SELECT @@transaction_isolation;

-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

### Q13: MVCC 是怎么实现的？解决了什么问题？

MVCC（多版本并发控制）让 **读不阻塞写，写不阻塞读**：

```
每行隐藏两个字段：
├── DB_TRX_ID（6字节）：最后一次修改这行的事务 ID
└── DB_ROLL_PTR（7字节）：指向 undo log 中上一个版本

UPDATE 流程：
  1. 对原行加 X 锁
  2. 将原行拷贝到 undo log
  3. 修改行数据，更新 DB_TRX_ID
  4. 其他事务通过 undo log 读取旧版本（快照读）
```

**ReadView（读视图）** 决定事务能看到哪些数据：

- READ COMMITTED：**每次 SELECT 生成新的 ReadView** → 能读到其他事务已提交的修改
- REPEATABLE READ：**事务开始时生成 ReadView** → 整个事务看到相同的快照

### Q14: 乐观锁和悲观锁的区别？在 MySQL 中如何实现？

|          | 悲观锁                  | 乐观锁                            |
| -------- | ----------------------- | --------------------------------- |
| 策略     | 假定别人会改，先锁      | 假定不会冲突，提交时检查          |
| 实现     | `SELECT ... FOR UPDATE` | 版本号/时间戳 `WHERE version = ?` |
| 并发性能 | 低（阻塞）              | 高（不阻塞）                      |
| 适用     | 写冲突多的场景          | 读多写少                          |

```sql
-- 悲观锁
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE; -- 锁定这行
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- 乐观锁
UPDATE accounts
SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 5; -- 版本号匹配才更新
-- 如果 affected rows = 0 → 冲突，重试
```

### Q15: 什么是间隙锁？MySQL 在什么情况下使用间隙锁？

间隙锁（Gap Lock）**锁定索引记录之间的间隙**，防止其他事务在间隙中 INSERT 新记录——解决幻读：

```sql
-- 表数据：id = 5, 10, 15
-- 查询：SELECT * FROM t WHERE id BETWEEN 5 AND 10 FOR UPDATE;
-- 锁住：id=5 的行 + (5,10) 间隙 + id=10 的行 + (10,15) 间隙
-- 其他事务无法插入 id=6,7,8,9,11,12,13,14
```

**只在 REPEATABLE READ 隔离级别下生效**（MySQL 默认）。READ COMMITTED 下间隙锁失效，通过 MVCC 解决不可重复读。

### Q16: 死锁是如何产生的？怎么排查和避免？

```sql
-- 经典死锁场景
-- 事务A：UPDATE accounts SET balance = balance - 100 WHERE id = 1;
--         UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- 事务B：UPDATE accounts SET balance = balance - 50 WHERE id = 2; -- ← 等待 A 释放 id=2
--         UPDATE accounts SET balance = balance + 50 WHERE id = 1; -- ← 等待 B 释放 id=1
-- → 相互等待，死锁！
```

**排查：**

```sql
SHOW ENGINE INNODB STATUS\G  -- 搜索 "LATEST DETECTED DEADLOCK"
SELECT * FROM information_schema.innodb_trx; -- 当前事务
```

**避免：**

- 所有事务按**相同顺序**访问资源
- 尽量缩短事务
- 合理设置索引（无索引时行锁退化为表锁）

## 四、SQL 优化

### Q17: 如何排查慢查询？

```sql
-- 1. 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 2; -- 超过 2 秒记录

-- 2. 查看慢查询
mysqldumpslow -s t slow.log  -- 按时间排序

-- 3. EXPLAIN 分析
EXPLAIN SELECT * FROM users WHERE email = 'alice@x.com';
-- 关注 type（const>ref>range>ALL）、key、rows、Extra

-- 4. MySQL 8.0 EXPLAIN ANALYZE（实际执行）
EXPLAIN ANALYZE SELECT ...;
-- 显示 real time + actual rows + loops
```

### Q18: 大表分页如何优化？

```sql
-- ❌ 慢：OFFSET 100000 需要扫描并丢弃前 10 万行
SELECT * FROM users ORDER BY created_at LIMIT 10 OFFSET 100000;

-- ✅ 方案一：延迟关联
SELECT u.* FROM users u
INNER JOIN (
  SELECT id FROM users ORDER BY created_at LIMIT 10 OFFSET 100000
) tmp ON u.id = tmp.id;

-- ✅ 方案二：游标分页（推荐，但不支持跳页）
SELECT * FROM users WHERE id > 100000 ORDER BY id LIMIT 10;
-- 记录上一页最后一条 id，下一页用 WHERE id > last_id
```

### Q19: JOIN 查询的优化要点？

```sql
-- 1. 小表驱动大表（优化器通常自动做，但要知道原理）
-- 2. 关联字段必须有索引
-- 3. 避免 SELECT *，只取需要的列 → 增加覆盖索引的可能
-- 4. 多表 JOIN 控制数量（≤ 3 个）
-- 5. 用 EXISTS 替代 IN（当子查询结果集大时）
```

## 五、架构与运维

### Q20: MySQL 主从复制的工作原理？

```
Master                           Slave
  │                                │
  │ 写入数据                       │
  ▼                                │
binlog (二进制日志)                │
  │                                │
  └──── IO线程拉取 ────▶ relay log │
                        (中继日志) │
                                   ▼
                        SQL线程重放 relay log
                        → 数据与 Master 同步
```

**三种复制格式：**

| 格式      | 说明          | 优缺点                                |
| --------- | ------------- | ------------------------------------- |
| STATEMENT | 记录 SQL 语句 | 日志小，但某些函数（NOW()）导致不一致 |
| ROW       | 记录行变更    | 更安全（推荐），日志大                |
| MIXED     | 混合          | 默认，MySQL 自动选择                  |

### Q21: 分库分表策略有哪些？

| 策略         | 说明                 | 示例                                     |
| ------------ | -------------------- | ---------------------------------------- |
| **垂直分库** | 按业务拆库           | 用户库、订单库、商品库                   |
| **垂直分表** | 按列拆分（冷热分离） | 用户主表（常用）+ 用户扩展表（不常用）   |
| **水平分表** | 按行拆分             | 按 user_id % 16 分到 16 张表             |
| **水平分库** | 跨库水平拆分         | user_id 0-499 万在 DB1，500-999 万在 DB2 |

**sharding key 选择原则：** 让大部分查询落在单个分片上。

### Q23: 速查表

**索引：**

| 场景           | 策略                                  |
| -------------- | ------------------------------------- |
| 高频查询单字段 | 单字段索引                            |
| 高频组合查询   | 复合索引（ESR 顺序）                  |
| 字段值唯一     | 唯一索引                              |
| 长字符串 LIKE  | 前缀索引                              |
| 只查某几列     | 覆盖索引（复合 + 包含所有 select 列） |

**SQL 优化口诀：**

1. `EXPLAIN` 看 type → ALL 必须优化
2. 索引遵循最左前缀
3. 避免 WHERE 中对列做函数/运算
4. JOIN 字段加索引
5. 大分页用游标或延迟关联
6. 只查需要的列（SELECT 列名，不用 \*）
