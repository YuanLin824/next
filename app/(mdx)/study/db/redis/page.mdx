# Redis 学习指南

> 难度递进式学习文档，覆盖从零基础到生产环境架构设计的完整链路，以 Redis 7.x 为例。

## 第一阶段：认识 Redis（入门）

### 1. Redis 是什么？

Redis（Remote Dictionary Server）是一个**基于内存的键值数据存储**，2009 年由 Salvatore Sanfilippo（antirez）创建。它把数据存在内存中，支持多种数据结构，主要用于缓存、消息队列、实时计算等场景。

```
PostgreSQL/MySQL：硬盘为主，内存是缓存层
Redis：           内存为主，硬盘是持久化层
```

**核心特征：**

| 特征             | 说明                                                            |
| ---------------- | --------------------------------------------------------------- |
| **纯内存**       | 读写速度 10万+ QPS，微秒级延迟                                  |
| **丰富数据结构** | String / Hash / List / Set / Sorted Set / Stream / Geo / Bitmap |
| **单线程模型**   | 6.0 前纯单线程，6.0+ I/O 多线程（但命令执行仍单线程）           |
| **持久化**       | RDB 快照 + AOF 日志，重启可恢复                                 |
| **高可用**       | 主从 + Sentinel + Cluster                                       |
| **原子操作**     | 每个命令都是原子的，Lua 脚本保证多步原子                        |

### 2. Redis 能做什么？

| 场景             | 使用方式                   | 对应数据结构          |
| ---------------- | -------------------------- | --------------------- |
| **缓存**         | 热点数据缓存，减少 DB 压力 | String / Hash         |
| **计数器**       | PV/UV 统计、接口限流       | String (INCR)         |
| **分布式锁**     | 多服务互斥访问资源         | String (SET NX)       |
| **消息队列**     | 服务间异步通信             | List (BLPOP) / Stream |
| **排行榜**       | 实时排名                   | Sorted Set            |
| **去重**         | 用户签到、标签             | Set / Bitmap          |
| **Session 共享** | 分布式 Session 存储        | Hash                  |
| **延时队列**     | 定时任务触发               | Sorted Set            |
| **实时统计**     | UV 去重计数                | HyperLogLog           |
| **地理围栏**     | 附近的人                   | Geo                   |

### 3. 安装（Docker）

```bash
docker pull redis:7-alpine

docker run -d -p 6379:6379 --name redis \
  -v /redis/data:/data \
  redis:7-alpine redis-server --appendonly yes

# 连接
docker exec -it redis redis-cli
```

**Docker Compose（带 ACL + 自定义配置）：**

```yaml
# docker-compose.yml
services:
  redis:
    image: redis:7-alpine
    container_name: redis
    ports:
      - "${REDIS_PORT:-6379}:6379"
    volumes:
      - redis_data:/data
      - ./redis.conf:/usr/local/etc/redis/redis.conf:ro
    command: redis-server /usr/local/etc/redis/redis.conf
    restart: unless-stopped

volumes:
  redis_data:
```

```conf
# redis.conf —— 关键配置
port 6379
bind 0.0.0.0
protected-mode yes

# 持久化
save 900 1
save 300 100
save 60 10000
appendonly yes
appendfsync everysec

# 内存
maxmemory 256mb
maxmemory-policy allkeys-lru

# 慢查询
slowlog-log-slower-than 10000       # 超过 10ms 记录
slowlog-max-len 128

# ACL（Redis 6.0+）
aclfile /usr/local/etc/redis/users.acl
```

```acl
# users.acl
user default off
user admin on >redis123 ~* &* +@all
user app on >app123 ~app:* &* +@read +@write +@connection +info
user readonly on >readonly123 ~app:* &* +@read +@connection +info
```

### 4. 连接与第一组命令

```bash
# 连接
docker exec -it redis redis-cli       # 本地连接
redis-cli -h 127.0.0.1 -p 6379 -a password  # 远程连接

# 认证
AUTH username password                # Redis 6.0+ ACL 认证
AUTH password                         # 旧式密码认证

# 测试
PING                                  # → PONG
```

```bash
# 第一组命令
SET name "redis"                      # 设置键
GET name                              # 获取键 → "redis"
EXISTS name                           # 判断是否存在 → 1
DEL name                              # 删除键 → 1
EXPIRE counter 60                     # 60 秒后过期
TTL counter                           # 查看剩余时间（-1 不过期，-2 已过期）
INCR views                            # 原子自增（不存在则创建为 0 + 1）
TYPE name                             # 查看键类型

# 通用操作
KEYS user:*                           # ⚠️ 生产禁用！数据量大时阻塞（用 SCAN 替代）
SCAN 0 MATCH user:* COUNT 100         # 游标式遍历（安全）
DBSIZE                                # 当前库键总数
```

### 5. Redis 的数据库

Redis 有 **16 个逻辑数据库**（编号 0-15），默认使用 0 号。注意：它们共享同一进程内的资源（内存、CPU、持久化），不是真正的物理隔离。

```bash
SELECT 1                              # 切换到 1 号库
SELECT 0                              # 切回 0 号（默认）
```

> 最佳实践：大多数场景只用 0 号库。多库难以区分业务、无法跨库操作、故障时一起挂。多业务隔离用不同 Redis 实例。

## 第二阶段：五种核心数据类型

### 6. String —— 万物皆字符串

String 是 Redis 最基础的类型，但不仅是字符串——它可以存任意二进制数据（最多 512MB）。

```bash
# ====== 基础操作 ======
SET key value
SET key value EX 60                   # 60 秒过期
SET key value NX                      # 不存在才设置
SET key value XX                      # 存在才覆盖
GET key
MSET k1 v1 k2 v2                      # 批量设置
MGET k1 k2                            # 批量获取

# ====== 计数器（最常用场景） ======
INCR page:home:views                  # 自增 → 1 → 2 → 3
INCRBY user:1001:score 10             # 加 10
DECR stock:sku123                     # 减 1
INCRBYFLOAT price:usd 0.5             # 浮点加减

# ====== 原子操作 ======
GETSET key newval                     # 设新值，返回旧值
SETNX key value                       # SET key value NX 的旧写法
APPEND key "suffix"                   # 追加内容
STRLEN key                            # 字符串长度
```

**实战：分布式锁**

```bash
# 获取锁（NX = 不存在才设；EX 10 = 10 秒自动释放，防死锁）
SET lock:order:1001 "unique_value" NX EX 10

# 释放锁（用 Lua 保证原子——只删除自己的锁）
EVAL "
  if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
  else
    return 0
  end
" 1 lock:order:1001 unique_value
```

### 7. Hash —— 对象的数据库行

Hash 适合存储对象——相比存 JSON 字符串，Hash 可以**按字段独立读写**，不用整存整取。

```bash
# ====== 基础操作 ======
HSET user:1001 name "Alice" email "alice@x.com" age 25
HGET user:1001 name                   # → "Alice"
HMGET user:1001 name age              # → "Alice", "25"
HGETALL user:1001                     # 获取全部字段和值
HDEL user:1001 age                    # 删除字段
HEXISTS user:1001 phone               # 是否存在 → 0
HLEN user:1001                        # 字段数
HKEYS user:1001                       # 所有字段名
HVALS user:1001                       # 所有字段值

# ====== 原子操作 ======
HINCRBY user:1001 age 1               # 年龄 +1
HINCRBYFLOAT user:1001 score 1.5      # 浮点自增
HSETNX user:1001 name "Bob"           # 不存在才设

# ====== 批量操作 ======
HSCAN user:1001 0 MATCH * COUNT 20    # 游标式遍历（大 Hash 用，避免阻塞）
```

**实战：缓存用户信息**

```bash
# 从 MySQL 加载用户数据到 Redis
HSET cache:user:1001 \
  id 1001 \
  username "alice" \
  email "alice@x.com" \
  avatar "https://cdn.example.com/avatars/alice.jpg" \
  vip_level 3

EXPIRE cache:user:1001 3600           # 1 小时过期

# 更新部分字段（不需要重新缓存整个对象）
HSET cache:user:1001 vip_level 4
```

### 8. List —— 队列与栈

List 是**有序**字符串链表，两端操作 O(1)，中间操作 O(N)。

```bash
# ====== 队列（FIFO） ======
LPUSH queue:tasks task1 task2 task3    # 左侧入队
RPOP queue:tasks                       # 右侧出队 → "task1"

# ====== 栈（LIFO） ======
LPUSH stack:undo "step1" "step2"
LPOP stack:undo                        # → "step2"

# ====== 阻塞队列（消息队列核心） ======
BLPOP queue:tasks 0                    # 阻塞等待新消息（0 = 永久等待）
BRPOP queue:tasks 5                    # 等待最多 5 秒

# ====== 查看与修改 ======
LRANGE queue:tasks 0 -1                # 全部元素
LLEN queue:tasks                       # 长度
LINDEX queue:tasks 0                   # 按索引取（O(N)）
LREM queue:tasks 1 "task1"             # 删除 N 个匹配值
LTRIM queue:tasks 0 99                 # 只保留前 100 条（限制队列长度）

# ====== 实战：可靠消息队列模式 ======
# 生产者
LPUSH queue:orders '{"id":1,"item":"phone"},{"id":2,"item":"laptop"}'

# 消费者
BRPOPLPUSH queue:orders queue:orders:processing 0
# → 从 queue:orders RPOP → 同时 LPUSH 到 queue:orders:processing
#   处理完成后从 processing 中 LREM 删除
#   如果消费者崩溃，processing 中的消息可被另一个消费者重新处理
```

### 9. Set —— 无序去重集合

Set 是无序字符串集合，**O(1) 判断存在**，支持交/并/差集运算。

```bash
# ====== 基础操作 ======
SADD tags:post:1 "redis" "nosql" "cache"
SMEMBERS tags:post:1                  # 所有成员
SISMEMBER tags:post:1 "redis"         # 是否存在 → 1
SREM tags:post:1 "cache"              # 删除
SCARD tags:post:1                     # 成员数
SSCAN tags:post:1 0                   # 游标式遍历

# ====== 集合运算 ======
SADD user:1:friends Alice Bob Charlie
SADD user:2:friends Bob David Eve

SINTER user:1:friends user:2:friends  # 交集（共同好友） → Bob
SUNION user:1:friends user:2:friends  # 并集（全部好友）
SDIFF user:1:friends user:2:friends   # 差集（1 独有的好友）

# ====== 随机操作（抽奖） ======
SPOP lottery:pool 1                   # 随机弹出 1 个（不重复抽奖）
SRANDMEMBER lottery:pool 3            # 随机取 3 个（不删除，重复抽奖）
```

**实战：标签去重、点赞用户**

```bash
# 用户 1001 点赞了文章 88
SADD article:88:likes user:1001
# 用户又点了一次（重复） → 自动忽略
SADD article:88:likes user:1001

# 文章点赞数
SCARD article:88:likes

# 用户是否点过赞
SISMEMBER article:88:likes user:1001
```

### 10. Sorted Set —— 排行榜引擎

每个成员绑定一个 **score**（浮点数），按 score 排序。score 相同则按成员字典序排。

```bash
# ====== 基础操作 ======
ZADD leaderboard 100 "Alice" 85 "Bob" 92 "Charlie"
ZRANGE leaderboard 0 -1 WITHSCORES                # 升序（低到高）
ZREVRANGE leaderboard 0 -1 WITHSCORES             # 降序 → 排行榜
ZSCORE leaderboard "Alice"                        # 分数 → "100"
ZRANK leaderboard "Alice"                         # 升序排名（0 开始）
ZREVRANK leaderboard "Alice"                      # 降序排名
ZREM leaderboard "Bob"                            # 删除
ZCARD leaderboard                                 # 成员数
ZINCRBY leaderboard 5 "Alice"                     # 分数 +5

# ====== 按分数范围 ======
ZRANGEBYSCORE leaderboard 80 100 WITHSCORES       # 80~100 分的成员
ZCOUNT leaderboard 80 100                         # 分数区间计数
ZREMRANGEBYSCORE leaderboard 0 60                 # 删除不及格成员

# ====== 并集/交集 ======
ZUNIONSTORE weekly_top 2 week1 week2 WEIGHTS 1 2  # 合并两个排行榜（week2 权重 2 倍）
```

**实战：延时队列**

```bash
# score 存储任务执行时间戳（毫秒）
ZADD delay:queue 1690700000000 "task:order:1001"
ZADD delay:queue 1690700030000 "task:order:1002"

# 取出到期的任务（score ≤ 当前时间）
ZRANGEBYSCORE delay:queue 0 1690700020000 LIMIT 0 10

# 取到后删除（原子操作两种方式）：
# 方式一：先取再删（非原子，有丢失风险）
# 方式二：Lua 脚本（推荐）
EVAL "
  local items = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, 10)
  if #items > 0 then
    redis.call('ZREM', KEYS[1], unpack(items))
  end
  return items
" 1 delay:queue 1690700020000
```

## 第三阶段：高级特性

### 11. 发布订阅（Pub/Sub）

```bash
# ===== 订阅者 =====
SUBSCRIBE channel:news                  # 订阅频道（阻塞等待）
PSUBSCRIBE channel:*                    # 模式匹配订阅

# ===== 发布者 =====
PUBLISH channel:news "服务器上线了"     # 发布消息 → 返回订阅者数量

# ⚠️ Pub/Sub 的局限性：
# - 消息不持久化：订阅者断线期间的消息会丢失
# - 没有 ACK 机制：发了就忘
# - → 对可靠性有要求用 Stream（见下文）
```

### 12. 事务 + 乐观锁

```bash
# Redis 事务: 一组命令排队一次执行，执行期间不会被其他命令插入

MULTI                                   # 开启事务
SET key1 "a"
INCR counter
HSET user:1 name "Alice"
EXEC                                    # 批量执行 → 返回每条结果
# 或 DISCARD                            # 取消事务

# 乐观锁（Check-And-Set）
WATCH balance                           # 监视 balance
GET balance                             # → "100"
MULTI
DECRBY balance 50
INCRBY spent 50
EXEC                                    # 如果 balance 被他人修改 → 返回 nil（不执行）
# 应用层收到 nil → 重试
```

**事务的局限性：**

- 不支持回滚——某条命令执行失败，其他命令照常执行
- 命令间没有中间结果引用——不能"如果 SET A 成功再 SET B"
- 复杂条件判断需要 **Lua 脚本**

### 13. Lua 脚本 —— 真正的原子多步操作

Lua 脚本在 Redis 内部作为一个整体执行，天然原子。

```bash
# EVAL script numkeys key [key ...] arg [arg ...]
EVAL "return redis.call('SET', KEYS[1], ARGV[1])" 1 mykey myvalue

# ===== 实战：令牌桶限流器 =====
EVAL "
  local key = KEYS[1]
  local capacity = tonumber(ARGV[1])      -- 桶容量
  local rate = tonumber(ARGV[2])          -- 每秒新增令牌
  local now = tonumber(ARGV[3])           -- 当前时间 ms

  local bucket = redis.call('HMGET', key, 'tokens', 'last_time')
  local tokens = tonumber(bucket[1]) or capacity
  local last_time = tonumber(bucket[2]) or now

  -- 计算新增令牌
  local elapsed = math.max(now - last_time, 0)
  tokens = math.min(capacity, tokens + elapsed * rate / 1000)

  if tokens >= 1 then
    tokens = tokens - 1
    redis.call('HMSET', key, 'tokens', tokens, 'last_time', now)
    redis.call('EXPIRE', key, 2)
    return 1                               -- 放行
  else
    return 0                               -- 限流
  end
" 1 ratelimit:api:login 10 5 1690700000000
```

**用 SCRIPT LOAD 缓存脚本（避免每次传输脚本体）：**

```bash
SCRIPT LOAD "return redis.call('GET', KEYS[1])"     # → "abc123"（SHA）
EVALSHA abc123 1 mykey                              # 后续调用直接用 SHA
```

### 14. Stream —— 持久化消息队列（5.0+）

Stream 是 Redis 对消息队列的正式回答——比 Pub/Sub 更持久，比 List 更专业。

```bash
# ===== 添加消息 =====
XADD mystream * field1 value1 field2 value2    # * = 自动生成 ID
# → "1690700000000-0"                          # ID = 毫秒时间-序号

# ===== 读取消息 =====
XRANGE mystream - + COUNT 5                    # 从头读 5 条
XREVRANGE mystream + - COUNT 5                 # 最新 5 条
XLEN mystream                                  # 消息数量

# ===== 消费者组（Consumer Group） =====
# 创建消费者组（$ = 从最新消息开始，0 = 从第一条开始）
XGROUP CREATE mystream mygroup $
# 消费者 C1 读取消息（> 表示从未传递过的消息）
XREADGROUP GROUP mygroup C1 COUNT 5 STREAMS mystream >
# 确认消息已处理（ACK）
XACK mystream mygroup 1690700000000-0
# 查看待处理消息（已分配但未 ACK——消费者挂了可以重新处理）
XPENDING mystream mygroup

# Stream vs List 对比：
# Stream: 消息持久化、消费者组、ACK 确认、消息回溯
# List:   简单队列、消费者挂了消息丢失、无 ACK
```

### 15. 其他高级数据类型

```bash
# ===== Bitmap —— 位图（统计签到、在线状态） =====
SETBIT user:1001:signin 0 1              # 第 0 天签到
SETBIT user:1001:signin 1 1              # 第 1 天签到
BITCOUNT user:1001:signin                # 签到天数 → 2
BITPOS user:1001:signin 0                # 第一个未签到天

# ===== HyperLogLog —— UV 去重统计（误差 0.81%，仅占 12KB） =====
PFADD page:home:uv user1 user2 user3
PFCOUNT page:home:uv                     # → 3（近似去重计数）
PFMERGE page:total:uv page:home:uv page:about:uv  # 合并多页 UV

# ===== Geo —— 地理位置（附近的人） =====
GEOADD locations 116.404 39.915 "天安门"
GEOADD locations 116.397 39.908 "故宫"
GEODIST locations "天安门" "故宫" m      # 两点距离（米）
GEORADIUS locations 116.4 39.91 5 km WITHDIST   # 5km 内的地点
GEORADIUSBYMEMBER locations "天安门" 10 km ASC  # 距天安门 10km 内的地点
```

## 第四阶段：持久化与内存管理

### 16. RDB 持久化 —— 快照

RDB 在指定时刻对整个数据集做**内存快照**，保存为二进制 `.rdb` 文件。

```conf
# redis.conf
save 900 1           # 900 秒内至少 1 次修改 → 触发快照
save 300 100         # 300 秒内至少 100 次修改 → 触发快照
save 60 10000        # 60 秒内至少 10000 次修改 → 触发快照
```

| 优点                              | 缺点                                          |
| --------------------------------- | --------------------------------------------- |
| 文件紧凑、恢复快                  | 两次快照之间的数据会**丢失**                  |
| 对读写性能影响小（fork 子进程写） | fork 时内存翻倍（copy-on-write 仍有一定开销） |

```bash
SAVE                  # 同步保存（阻塞！生产禁用）
BGSAVE                # 后台异步保存（不阻塞，推荐）
LASTSAVE              # 上次成功保存的时间戳
```

### 17. AOF 持久化 —— 操作日志

AOF（Append Only File）把每一条**写命令**追加记录到日志文件，重启时重放。

```conf
# redis.conf
appendonly yes
appendfsync always     # 每次写入都 fsync → 最安全，性能最低
appendfsync everysec   # 每秒 fsync 一次 → 折中，推荐
appendfsync no         # 交给 OS → 性能最高，可能丢数据
```

| 优点                 | 缺点                     |
| -------------------- | ------------------------ |
| 最多丢 1 秒数据      | AOF 文件大（随时间增长） |
| 可读文本（方便调试） | 恢复速度比 RDB 慢        |

**AOF 重写（压缩）：**

```conf
# 当 AOF 文件增长到上次重写后的 100%，且大于 64MB 时触发
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

```bash
BGREWRITEAOF          # 手动触发重写
```

### 18. 混合持久化（Redis 4.0+，推荐）

```conf
aof-use-rdb-preamble yes
```

> 混合持久化 = RDB 快照（当前状态）+ AOF 增量日志（快照后的写操作）。文件开头是 RDB 二进制格式，后面追加 AOF 文本格式。兼具 RDB 的恢复速度和 AOF 的数据安全性。

**生产推荐方案：**

| 场景               | 方案                                                                   |
| ------------------ | ---------------------------------------------------------------------- |
| 纯缓存（数据可丢） | 关闭持久化，`maxmemory-policy allkeys-lru`                             |
| 需要持久化         | `appendonly yes` + `appendfsync everysec` + `aof-use-rdb-preamble yes` |

### 19. 内存淘汰策略

当 `maxmemory` 达到上限时，Redis 根据策略决定删除哪些键：

```conf
# redis.conf
maxmemory 512mb
maxmemory-policy allkeys-lru   # 推荐
```

| 策略              | 行为                           | 适用场景                            |
| ----------------- | ------------------------------ | ----------------------------------- |
| `noeviction`      | 拒绝写入，返回错误             | 数据不能丢（不推荐——会直接报错）    |
| `allkeys-lru`     | 淘汰任意键中**最近最少使用**的 | **通用缓存（推荐）**                |
| `allkeys-lfu`     | 淘汰任意键中**使用频率最低**的 | 热点缓存                            |
| `allkeys-random`  | 随机淘汰任意键                 | 基本不用                            |
| `volatile-lru`    | 淘汰**带过期时间**的键中的 LRU | 混合场景（不带 TTL 的键不会被淘汰） |
| `volatile-lfu`    | 同理，LFU 版本                 | 混合场景                            |
| `volatile-random` | 随机淘汰带 TTL 的键            | 混合场景                            |
| `volatile-ttl`    | 淘汰**最快过期**的键           | 混合场景                            |

### 20. 过期删除策略

Redis 使用两种策略配合：

| 策略         | 行为                                     |
| ------------ | ---------------------------------------- |
| **惰性删除** | 访问 key 时检查是否过期，过期则删        |
| **定期删除** | 每 100ms 随机抽取一批 key 检查，过期则删 |

> 这就是为什么 `TTL` 有时返回负数但 key 还存在——它还没被删。也是大 key + 大量过期可能导致短暂延迟的原因。

### 21. 主从复制

```
┌──────────┐     全量RDB + 增量AOF    ┌──────────┐
│  Master  │ ──────────────────────▶  │  Slave   │
│ (写+读)  │                          │  (只读)  │
└──────────┘                          └──────────┘
```

```bash
# 在 Slave 上执行
REPLICAOF master_ip master_port       # 成为指定 Master 的从库
REPLICAOF NO ONE                      # 脱离主从，变回独立实例

# 查看状态
INFO replication
```

```conf
# redis.conf（Slave 配置）
replicaof 192.168.1.100 6379
replica-read-only yes                 # 从库只读（推荐）
```

**复制流程：** Slave 发起 `PSYNC` → Master fork 子进程生成 RDB 发给 Slave → 后续增量命令通过 AOF 日志流持续同步。

### 22. Sentinel 哨兵 —— 自动故障转移

Sentinel 是 Redis 官方的 HA 方案，它**监控**主从实例，在 Master 故障时**自动选举新 Master**。

```
┌──────────────────────────────────────────┐
│              Sentinel 集群               │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│  │Sentinel 1│ │Sentinel 2│ │Sentinel 3│  │    至少 3 个（奇数，避免脑裂）
│  └──────────┘ └──────────┘ └──────────┘  │
│       │            │            │        │
│       └────────────┼────────────┘        │
│                    │ 监控 & 故障转移     │
│           ┌────────┴────────┐            │
│           │  Master / Slave │            │
│           └─────────────────┘            │
└──────────────────────────────────────────┘
```

**Sentinel 核心职责：**

- **监控**：定期 PING，超时未回复则标记主观下线
- **通知**：Master 故障时通过 Pub/Sub 通知客户端
- **自动故障转移**：选举新 Master，通知所有 Slave 复制新 Master

### 23. Cluster 集群 —— 数据分片

Cluster 通过**哈希槽**（hash slot）将数据分布到多个节点：

```
Redis Cluster 共有 16384 个槽

Node 1: slot 0~5460       (5461 个)
Node 2: slot 5461~10922   (5462 个)
Node 3: slot 10923~16383  (5461 个)

计算 key 属于哪个槽：
HASH_SLOT = CRC16(key) % 16384
```

```conf
# redis.conf（Cluster 模式）
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 5000
```

```bash
# 创建集群（在任一节点执行）
redis-cli --cluster create \
  192.168.1.1:6379 192.168.1.2:6379 192.168.1.3:6379 \
  192.168.1.4:6379 192.168.1.5:6379 192.168.1.6:6379 \
  --cluster-replicas 1   # 每个 Master 有 1 个 Slave

# 检查集群状态
redis-cli --cluster check 192.168.1.1:6379
```

> **注意**：Cluster 模式下多键操作（`MGET`、事务、Lua）要求所有 key 在同一个 slot。用 `{}` 强制相同 slot：`user:{1001}:name` 和 `user:{1001}:age` 会落在同一节点。

## 第六阶段：工程实践

### 24. 缓存三大问题

| 问题         | 描述                                           | 解决方案                                                            |
| ------------ | ---------------------------------------------- | ------------------------------------------------------------------- |
| **缓存穿透** | 查一个数据库中也不存在的 key → 每次都穿透到 DB | **布隆过滤器**过滤不存在的 key；或缓存空值（TTL 很短）              |
| **缓存击穿** | 热点 key 过期瞬间 → 大量请求打到 DB            | **互斥锁**：只有一个请求去加载 DB，其余等待；或"永不过期"+ 异步刷新 |
| **缓存雪崩** | 大量 key 同时过期 → DB 瞬时压力过大            | TTL 加随机值（如 `EXPIRE + RAND(0,300)`）；多级缓存；限流降级       |

```bash
# 缓存穿透：缓存空值
SET cache:user:notexist "null" EX 60

# 缓存击穿：互斥锁（SET NX）
# 线程发现缓存过期 → 尝试获取锁
# 获取成功 → 查 DB → 回填缓存 → 释放锁
# 获取失败 → 等待 → 重试缓存

# 缓存雪崩：TTL 加随机
EXPIRE cache:hotkey 3600 + (RANDOM % 300)
```

### 25. 分布式锁 —— Redlock 算法

单实例分布式锁有风险（主从切换时锁丢失）。Redlock 算法（Redis 作者提出）要求在 N/2+1 个独立 Redis 节点上成功获取锁才算成功。

**工程建议：** 对一致性要求不极端的场景，**单实例 + 合理 TTL + 唯一令牌**够用。真正要求极强一致性的场景（金融交易），考虑 ZooKeeper / etcd。

### 26. 缓存一致性

```
Cache-Aside 模式（旁路缓存，最常用）：

读：
1. 先查缓存 → 命中返回
2. 缓存未命中 → 查 DB
3. 将 DB 数据写入缓存

写：
1. 先更新 DB
2. 再删缓存（不是更新缓存！）
   原因：删缓存是无状态的，避免了并发更新的数据竞争
```

**删除缓存失败怎么办？** 用**延迟双删**或**订阅 binlog**（如 Canal）异步删除，保证最终一致性。

### 27. 大 Key 与热 Key

```bash
# ===== 大 Key 排查 =====
redis-cli --bigkeys                                  # 扫描最大的 key

# 或
redis-cli MEMORY USAGE user:999999999                # 单个 key 内存占用

# ===== 大 Key 处理 =====
# String 大 Key → 分片存储（如 user:1001:info 拆成多个 Hash 字段）
# Hash 大 Key → HSCAN 分批读，避免 HGETALL
# List/Set 大 Key → 拆分成多个小集合

# ===== 热 Key 排查 =====
redis-cli --hotkeys                                  # 扫描访问频率最高的 key

# 热 Key 处理：
# - 多副本缓存（把读压力分散到多个 Slave）
# - 本地缓存（如 Caffeine / Node.js Map，短 TTL）
# - 对请求做随机过期时间，避免同时失效
```

### 28. Node.js 中使用 Redis

```js
// ioredis —— Node.js 最成熟的 Redis 客户端
const Redis = require("ioredis")
const redis = new Redis({
  host: "localhost",
  port: 6379,
  password: "app123",
  db: 0,
  retryStrategy(times) {
    return Math.min(times * 50, 2000) // 重试策略
  },
})

// ===== 基础操作 =====
await redis.set("key", "value", "EX", 60)
const val = await redis.get("key")

// ===== 管道（批量命令，减少 RTT） =====
const pipeline = redis.pipeline()
pipeline.set("k1", "v1")
pipeline.incr("counter")
pipeline.get("k1")
const results = await pipeline.exec()
// → [[null, 'OK'], [null, 1], [null, 'v1']]

// ===== Lua 脚本 =====
const limiterScript = `
  local key = KEYS[1]
  local now = tonumber(ARGV[1])
  local limit = tonumber(ARGV[2])
  local window = tonumber(ARGV[3])

  redis.call('ZREMRANGEBYSCORE', key, 0, now - window * 1000)
  local count = redis.call('ZCARD', key)
  if count < limit then
    redis.call('ZADD', key, now, now .. '-' .. math.random())
    redis.call('EXPIRE', key, window)
    return 1
  end
  return 0
`
// 滑动窗口限流：每秒最多 5 次
const allowed = await redis.eval(limiterScript, 1, "ratelimit:api:user:1001", Date.now(), 5, 1)

// ===== 分布式锁（Redlock 简化版） =====
const { v4: uuid } = require("uuid")

async function acquireLock(resource, ttl = 10000) {
  const token = uuid()
  const ok = await redis.set(`lock:${resource}`, token, "NX", "PX", ttl)
  return ok ? token : null
}

async function releaseLock(resource, token) {
  const script = `
    if redis.call('GET', KEYS[1]) == ARGV[1] then
      return redis.call('DEL', KEYS[1])
    end
    return 0
  `
  await redis.eval(script, 1, `lock:${resource}`, token)
}
```

### 29. 常见陷阱与最佳实践

| 陷阱                          | 说明                                            | 正确做法                                     |
| ----------------------------- | ----------------------------------------------- | -------------------------------------------- |
| `KEYS *` 生产使用             | 单线程阻塞，数据量大时卡几秒甚至几十秒          | 用 `SCAN` 游标式遍历                         |
| 大 Key                        | 单 key 几 MB → 删除时阻塞、网络传输慢、内存碎片 | 大 Hash 分片、value 不超过 10KB              |
| 热 Key                        | 单个 key QPS 极高 → 单点瓶颈                    | 多副本、本地缓存                             |
| 所有数据不过期                | 内存无限增长 → OOM                              | 设置 `maxmemory` + 淘汰策略                  |
| 关闭持久化 + 用做主存储       | 重启数据全部丢失                                | 做缓存用可关，做主存储必须开 AOF             |
| 没有 ACK 就删消息             | 消费者处理失败 → 消息丢失                       | Stream 消费者组 + ACK / List + 备份队列      |
| 长事务/Lua 脚本               | 单线程下长时间阻塞                              | Lua 脚本要短小——执行时间控制在毫秒级         |
| `FLUSHALL` / `FLUSHDB` 无密码 | 删库跑路                                        | 生产环境禁用（`rename-command FLUSHALL ""`） |

### 30. 速查表

**五种数据类型速查：**

| 类型       | 存储     | 独特操作            | 经典场景               |
| ---------- | -------- | ------------------- | ---------------------- |
| String     | 字符串   | `INCR`, `SET NX EX` | 缓存、计数器、分布式锁 |
| Hash       | 字段-值  | `HINCRBY`, `HSETNX` | 对象缓存、Session      |
| List       | 有序链表 | `BLPOP`, `LTRIM`    | 消息队列、最新列表     |
| Set        | 无序集合 | `SINTER`, `SPOP`    | 标签、去重、抽奖       |
| Sorted Set | 有序集合 | `ZRANGE`, `ZINCRBY` | 排行榜、延时队列       |

**持久化速查：**

| 方案     | 安全性      | 恢复速度 | 生产建议   |

| 纯 RDB   | 可能丢数据  | 快       | 配合 AOF   |
| 纯 AOF   | 最多丢 1 秒 | 慢       | `everysec` |
| **混合** | 最多丢 1 秒 | 快       | ✅ 推荐    |
